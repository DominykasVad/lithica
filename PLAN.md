# PLAN.md

Roadmap for turning this szurubooru fork into **Lithica**, a booru engine
with support for optional modules.
How to work is in `AGENTS.md`. Background is in `ANALYSIS.md` (local only, may be absent).

Scope: **server modernisation, phases 0–3**, ending in release tag `v0.1.0`.

Tick a box only when the task meets the definition of done in AGENTS.md.

---

## Decisions

Settled with the owner on 2026-10-10.

| Topic | Decision |
|---|---|
| Fork model | Hard fork at upstream `10ac850`. No upstream remote, no cherry-picks. Upstream is reference-only. |
| Names | Engine **Lithica** (Python package `lithica`). GitHub repo `DominykasVad/lithica`. |
| Default branch | `main`. |
| Repo structure | One repo: engine + optional modules. Engine never imports modules. |
| Server language | Python 3.13 (no Rust rewrite). |
| Packaging | uv for everything: project, lockfile, dev env, Docker build. `lithica` is a `uv_build` package, flat layout (no `src/`). |
| Web framework | **FastAPI** (replaced the custom WSGI micro-framework `rest/` in phase 2). Endpoints return the serializers' output through `JsonResponse`; response models only document it, so the wire format cannot drift. Request bodies are read by our own dependency, not FastAPI's: the JSON may be the `metadata` part of a multipart request. |
| API docs | `doc/openapi.json`, generated by `python -m lithica.openapi` and enforced by CI, is the contract. Swagger UI at `docs`, ReDoc at `redoc` and `openapi.json` are served only with `api_docs` (default off; the development image sets `API_DOCS=1`); the pages load assets from a CDN. |
| Lint / format | ruff (replaces black, isort, flake8). Committed migrations (`lithica/migrations/versions/`) are excluded, never rewritten. `T20` bans `print`; `lithica-admin` is exempt. |
| Type checking | pyright, `basic` first, raised to `strict` per module. |
| Database | PostgreSQL 17 is the only tested/shipped database. Code stays DB-agnostic (SQLAlchemy only, see AGENTS.md). |
| Base image | Debian slim + uv (replaces Alpine system packages). Images run the source from `/opt/app` via `PYTHONPATH`; the environment is in `/opt/venv`; the package itself is not installed. |
| Registry / CI | GitHub Actions. Images to GHCR, built **only on published GitHub releases**, image tag = release tag. Docker Hub workflow removed. |
| Old client | Removed 2026-11 (decision [0012](doc/design/decisions/0012-legacy-client-removed.md)). |
| Module data model | One engine-owned generic table, `post_content`: post id + content kind + schema version + JSON payload. A module is the package `lithica.modules.<name>` exposing one `registry.Module` named `module`; it provides extractors, auto-tagging, search tokens, post fields, routes and admin commands, and never replaces anything of the engine (a clash is a startup error). |

### Further defaults

Confirmed by the owner on 2026-10-10.

- Debian release: `python:3.13-slim-trixie` (Debian 13).
- ASGI server: **uvicorn** (replaced waitress; `--reload` replaced hupper), started by `python -m lithica.serve`, which opens the listening socket itself. `HOST` (default `::`, IPv4 and IPv6), `PORT`, `WORKERS` (default 1; more is not verified yet). `THREADS` sizes the request thread pool.
- Image architectures: `linux/amd64` and `linux/arm64`. **`arm/v7` dropped** (pillow-heif already needed pinning for it).
- Versioning: SemVer tags `vMAJOR.MINOR.PATCH`; `v0.x` until the owner calls it stable. Fork point tagged `fork-point` at `10ac850`.
- Line length 88.
- Password reset tokens: SHA-256 of a 256-bit random token is stored, one pending token per user, the row is deleted on use. Lifetime is `password_reset_token_lifetime` seconds (default 3600). The mailed link is built from `domain` only; SMTP without `domain` is a startup error.
- CORS is answered by the server from `cors_origins`: exact origins only, `*` is a config error, empty means same origin.
- Limits on external work are constants, not settings: ffmpeg/ffprobe 600 s, yt-dlp 60 s, downloads 30 s per step, 300 s in all and 5 redirects.
- Downloads (`contentUrl`): `http`/`https` only; non-public addresses are refused at every hop unless `allow_private_downloads` is set; proxy environment variables are not used.
- Backfills of existing posts run from `lithica-admin backfill`, never from the server; the server only warns at startup.
- No in-process query cache. The one remaining per-process cache is the disk usage figure in `/info` (one hour).
- SQLAlchemy is held below 2.1: 2.1 defaults to psycopg 3, and the driver stays `psycopg2` until a task changes it.
- Module boundary check: **import-linter** (ruff's banned-imports rule cannot express "package A must not import package B" cleanly).
- `doc/API.md` holds the narrative (authentication, uploads, error model, resources, search syntax). The endpoint reference is the handlers' docstrings, published through OpenAPI.
- Uploads, downloads and stored files are file-backed `Content` (`lithica.func.content`); data the server makes itself stays `bytes`; code takes either. Temporary files live in `<data_dir>/temporary-uploads/.tmp/` and become stored files by rename.
- The largest request is `max_upload_size` (default 1 GiB, the limit of the client image's nginx; change both together).
- The database session is scoped per request by a ContextVar; work outside a request opens `db.session_scope()`.
- Modules load when `lithica.app` is imported (their routes are part of the application). Module routes live under `/modules/<name>/` and are in `doc/openapi.json`, each tagged with its module's name and nothing else: a module router that sets tags of its own is a startup error. The contract is generated with every module in `lithica/modules/` enabled (`registry.available()`), whatever the settings; the document a site serves under `api_docs` has the modules of that site.
- A content kind is at most 64 characters and belongs to exactly one module (`registry.ContentKind`).
- An extractor returns at most 64 results. A payload may be 1 MiB of JSON unless its kind asks for more (`ContentKind.max_payload_size`, hard cap 32 MiB; more is a startup error). Beyond a limit, or with one bad result, the extractor counts as failed and all its results for the file are dropped.
- An extractor or a detector refuses a file on purpose by raising `registry.FileRejected`: the upload is refused with its message. Anything else a detector raises counts as "not mine", and anything else an extractor raises is logged and skipped. On `reextract` a refusal counts as a failure and the rows are kept. Extraction runs before a post's signature is made, so a refused file leaves nothing in the session.
- `post_content.payload` is a deferred column: rows load without it, and it is fetched when read (a payload may be megabytes).
- `lithica-admin import`: each file is its own transaction; a duplicate is skipped by the upload path's checksum check. "Refused" is a validation or processing error of the file (exit 0), "failed" anything else (exit 1). Files and folders whose names start with a dot are left out; symlinked folders are not followed. No privilege of `--user` is asked (the command is the administrator's); snapshots are the user's. `--dry-run` checks duplicates, the file type and module refusals; it does not decode pictures.
- `lithica-admin create-user`: administrator on a site with no account, else regular; the password asked twice on a terminal or read from stdin (`--password-stdin`), never an argument, never read off a pipe unasked; the site's name and password rules; any `visibility`.
- A login token that does not work is `InvalidTokenError` (403), also for an unknown user, so clients need not read text.
- Module post fields are in the contract: `post_field_schemas` per module, nullable, on `Post`.
- `GET /info` says `maxUploadSize` and `acceptedTypes` (engine + enabled modules): hints for clients only.
- Implicit tags are inserted at once in a connection savepoint (Core); on a name conflict, the tag that won is taken.
- `fields` is checked against the resource's serializer by a dependency, before the endpoint runs.
- A search's user is an argument of `Executor.execute`/`get_around`; executors and configs keep nothing.
- Password reset: a site that cannot mail answers 500 `MailNotConfiguredError` (Server configuration error), for any name and before a token is made. Otherwise the request answers 200 `{}` whatever the account, and the confirmation one `InvalidPasswordResetTokenError` whatever was wrong (one query, no account lookup first). The mail is sent after the answer; one that fails is logged by its error's class only. At most one mail per account per `password_reset_mail_interval` (300 s), read from the pending token's creation time (no table); a used token ends the window.
- Development: `--reload` watches only the `lithica` package, by watchfiles events (dev dependency group), not polling.
- `MODULES` (comma-separated, in the environment) replaces `modules` of the config files when set; empty means none.
- Module file types (`registry.FileType`): asked only about files the engine refuses as `application/octet-stream`, in config order. The post type may not be an engine type nor one of its `type:` search aliases (`gif`, `webm`, ...); the MIME type must fit the 32 characters of `post."mime-type"` (checked at startup, no migration) and may not be the engine's. The stored file is the upload, byte for byte.
- Posts of a module file type: no canvas size, no default flags; found by `type:<post type>`. The thumbnail is the picture the module's hook returns, which must be an engine image type of at most 32 MiB; otherwise the engine's existing empty thumbnail (`EMPTY_PIXEL`). A signature, and so similar-image search, exists only with such a picture.
- A stored file's extension is asked of every module in `lithica/modules/`, switched on or not (read once per process); `dat` only if none knows the MIME type. Where a stored file is never depends on the settings.
- `Module.requested_post_fields`: post fields returned only when the request names them in `fields`. `Module.post_fields` are part of the default set.
- New content replaces every `post_content` row of the post, also rows of kinds no loaded module owns. `lithica-admin reextract` replaces only rows of kinds loaded modules own, keeps the old rows where an extractor fails, and never tags.
- Auto-tags are added on post create and on content change, never removed, and need no `tags:create` privilege. Their category is used only when the tag is created; a category the site lacks means the default one.
- `GET /post/<id>/content` needs `posts:view`. Rows of kinds no loaded module owns are stored but never shown. Private payload fields are top-level keys per kind, behind the one privilege `posts:view:content:private` (default moderator).

### The cards module

Settled during phase 4 (owner decisions marked).

- **Formats.** PNG: `tEXt` chunks `ccv3` (V3) and `chara` (V2, V1); `zTXt` and `iTXt` are read the same way. Order of reading: the first readable `ccv3`, else the first readable `chara`; of several chunks with one keyword the first readable one is the card (Chub writes its current version first, the original's chunk behind it); position decides, never size (owner). `ccv3` holds V3 cards only; a card in `chara` is of the version its `spec` says (no `spec`: V1). CHARX: a ZIP with a V3 `card.json` at the root, stored as `application/x-charx`, extension `charx`, post type `charx`.
- **What a card is.** A card needs a name (V1: and one more V1 field); other missing fields are fine, as real cards leave them out. Malformed card data in a picture means no card, and the picture is an ordinary picture.
- **Payload** (schema version 3): `{format, chunk, card, assets, summary, ignoredChunks}`. `ignoredChunks` lists the card chunks not used: keyword, position (chunk number in the file), size. `card` is the JSON as given, minus embedded binary data: a base64 data URI becomes `{"embedded": {type, name, size}}`, and inside a longer text it is cut out and marked. NUL characters and lone surrogates are removed (PostgreSQL cannot store them). `assets` lists paths and sizes only (PNG: `chara-ext-asset_:` chunks, at most 1000; CHARX: the archive's entries besides `card.json`). `chunk` is null for CHARX. `summary` is name, creator, greetings and lorebookEntries; search and the `card` post field read only it.
- **Size** (owner). The card kinds ask for 16 MiB of payload. A card over that refuses the upload, PNG and CHARX alike, and so does a card chunk over the 32 MiB that are read of one. A CHARX post is never stored without its card.
- **ZIP safety.** Entries are read from the archive into memory, never extracted. Limits: 1000 entries, 512 MiB unpacked, 100:1 per entry, `card.json` 8 MiB, table of contents 1 MiB, icon 16 MiB; stored and deflate only; no encrypted entries, no absolute or `..` paths, no archive as the icon. Only a ZIP with a root `card.json` is judged by the limits; any other archive is refused as an unknown file.
- **Thumbnail of a CHARX post.** The icon named `main`, else the first icon, from `embeded://`, `embedded://`, `__asset:` or a base64 `data:` URI. An icon elsewhere (`https:`) is never fetched.
- **Tags.** Creator → category `creator` (made by the site's admin; else the engine's missing-category rule), the card's own tags → the default category; lower case, whitespace as `_`. A post gets the creator and at most 99 of the card's tags, because the engine takes 100 tags from one module.
- **Search.** Greetings = the first message, if not empty, plus the alternate greetings; group-only greetings do not count. `card-lorebook:yes` means at least one entry. `card-creator:` matches the creator as the card has it, not the tag. The tokens are unindexed JSON lookups: fine for a personal library, no index for now.
- **Download.** A plain route, not an `ApiRouter` one: it needs no `Accept: application/json`, and its errors are JSON. Names: at most 100 characters, NFC, no control or format characters, no path or Windows-reserved characters; ASCII `filename` plus `filename*`; fallback `card-<id>`. The name comes from the summary; the card is not read for a download.

### Visibility and signed file links

Settled in phase 5 (5.6b, 5.7).

- **`visibility`**: `open`, `nsfw-login`, `login`. In `login` the anonymous rank has no privileges (so no sign-up), and an app dependency answers 403 to everything but `GET /info`, logging in and password reset.
- **NSFW posts**: those with `nsfw_tag` (any of its names) or any tag implying it, transitively; worked out once per request. The post field `nsfw`, from the same set, is the one answer to "is this post NSFW" for clients.
- **`nsfw-login` hides in one place**: loader criteria on Post, Comment, Snapshot, PoolPost and PostFeature. A request is filtered until `get_user` names somebody (fail closed); the CLI and background jobs are not filtered. Queries that select all posts select columns, never entities (the identity map would hand hidden ones out). Tag siblings, a post's `relationCount` and a pool's `postCount` leave hidden posts out; tag usages and a user's upload, favourite and comment counts count them; documented.
- **`nsfw_hide_names`**: a hint for clients in `/info`, not a filter; revealing a post shows the names too.
- **Signed file links**: nginx's `secure_link_md5` of `"<e></path under /data> <secret>"`, `e` the start of the day after tomorrow, UTC. `FILE_LINK_SECRET` is `[A-Za-z0-9_-]{32,}`, checked by the server and the client image; one `.env` value for both. Not `open` and no secret: a warning at start, not a refusal.

### Sardonyx

Settled in phase 5, for `clients/sardonyx`.

- **Toolchain.** TypeScript 6.0, not 7 (openapi-typescript needs the compiler API 7 does not have). pnpm 12.15.0; in the image pnpm's own binary, checked by SHA-256 (Node 26 has no corepack). shadcn/ui's `cn` package replaces clsx + tailwind-merge. Code-based TanStack routes. The API base URL is `api/` beside the app, made absolute.
- **Image.** nginx passes `/api/` on as sent (still encoded) and resolves the server at each request; gzip for JSON, JS, CSS and SVG from 1 KB, uploads and downloads sent as stored. Served at the root of its host: no base path; a `BASE_URL` with a path is warned about at start and ignored. Dev stack: the image on port 8082; `pnpm dev` proxies to the stack's client on 8080 (`LITHICA_URL`).
- **Session.** `sardonyx.session`: sessionStorage, the token expires in 24 h; "remember me": localStorage, 90 days. The session ends on an `InvalidTokenError` only, by its name; a refused privilege (`AuthError`) leaves it. Logout forgets the token here first, then deletes it on the site; a failure there is shown, not fatal.
- **Look.** Theme light, dark, system or Dracula, per browser (`sardonyx.theme`), applied by `public/theme.js` (no inline script under the CSP). The palette comes from the design reference, with the roles `link`, `macro`, `ok`, `warn`; components use roles only. Every theme passes `src/app/palette.test.ts`: text roles reach 4.5:1 on their backgrounds, control edges (`--control-border`) 3:1 (WCAG 1.4.11). Dracula: `.dracula` with `.dark`, destructive `#ff7979`, control edges `#8087a8`. Errors: everything a request throws is an `ApiError` (title, description, status), shown by one component. The design reference in `docs/design/` is read-only, outside lint, the image and CI.
- **Library.** `/posts` (`/` stays the start page); one URL for both modes, `?q=<query>&at=<offset of the first result>`. "Per page" 50, 100 or Auto load, per browser (`sardonyx.perPage`, default Auto load). A page change or a new search pushes a history entry; scrolling in auto load replaces `at`. Auto load asks 100 at a time, batches aligned to multiples of 100, one query per batch keyed by offset, the batches in the window ±1 asked once scrolling rests 150 ms, the total of the newest answer; the row height is fixed per search from its first batch (cards or not); the place a scroll goes is taken when it is made. Below `sm` the header's pages fold into a menu, below `md` the card filters behind "Filters (n)".
- **Search.** The query text is the only truth: card filters are read from it and change only their own `card-*` tokens; the creator filter writes spaces as `*` and shows `*` as a space. Completion: the token at the cursor; `<prefix>* sort:usages`, 10, after 150 ms; the tag escaped.
- **Post page and card text.** URL `?q=&at=&tab=` (q and at are the way back and prev/next; tab replaces). Tags shown once: the post's, by category; the default category has no heading. Card text modes Readable, Source and Styled per browser (`sardonyx.cardText`, default Readable; old "formatted"/"plain" read as readable/source). Markdown without a raw-HTML plugin; images as `[image: alt]`, never loaded; Readable shows HTML as its text. Links show their URL; only http(s) is a link (new tab, `noopener noreferrer nofollow ugc`). Macros `{{…}}` shown as written in the macro role, never replaced. Lorebook URL `?filter=&kind=` (replace; filter once typing rests 300 ms); mode: constant = always active, selective flag + secondary keys = selective, else keyword.
- **Download.** Fetched with the session, saved as `Content-Disposition` names it, else `<id>.<ext>`; the token goes only to the page's origin; the blob URL is revoked 60 s after the click.
- **Styled.** Card HTML in a frame sandboxed `allow-scripts allow-popups allow-popups-to-escape-sandbox`, which takes its HTML by postMessage from its parent only; the page takes only its height. The frame's one script is named by sha256 hash, not `'self'`. Two frame policies, one page under two paths: images off (`data:` only) and on (`https: data:`). Card pictures load only when the viewer asks, per card; hosts read from the text; the choice is not kept. The frame drops script, meta, base, link, frames, objects, `on*` and non-http(s) link hrefs.
- **Upload.** `POST /uploads` by XMLHttpRequest (real progress), then `POST /posts` with the token, 2 at a time. Up front a file is refused only when sure: over `maxUploadSize`, or a well-known extension not listed. Cancel stops the sending only; `POST /posts` is never aborted and its outcome is shown. The link and page need `uploads:create` and `posts:create:identified`. The NSFW box per file sets the site's NSFW tag in the tags sent; a card whose own tags carry it pre-checks and holds the box, with a note; card tags are read in the browser (at most 10,000 PNG chunks, none past the file's end), only where `cards` is on.
- **Editing.** A field only under its own privilege (`posts:edit:tags`/`safety`/`source`); only changes are sent. A 409 offers Reload: the fields show the post as it now is, the unsaved edit beside them; never merged. After a save, list entries take the post's new values and lists are marked stale; a delete drops it. Delete: an inline confirmation naming post and card; DELETE with version; back to the library's q and at. Focus: editor → its first field, confirmation → Cancel; Escape cancels; closing → the button that opened it. Tags: the completion field as a wrapping textarea (grows to 192 px). Privilege names as `GET /info` gives them (camelCase), held to `config.yaml.dist` by a test. `/tags` `?q=&category=&at=`, 50 a page, `sort:usages` unless the query sorts, needs `tags:list`; "Create the creator category" with cards on, no `creator` and `tagCategories:create`, colour `#7e2f22`.
- **NSFW.** Blurred by the post field `nsfw` only; a tile keeps its card's name and creator unless `nsfwHidesNames`. Show NSFW: localStorage per browser, off by default; a reveal lasts the tab's session. In `login` mode the shell draws only the login form (and password reset) until logged in; no page before `/info` answers.
- **Password reset and account.** The mail's link: the token is taken off the address at once (history entry replaced) and kept in memory; the image's nginx keeps that page out of the access log, with no referrer. Every answer of the request but `MailNotConfiguredError` reads as "sent". `/account` checks the current password by reading the account with it (Basic), then PUTs with the version.
- **Browser tests.** Playwright against the dev stack + `docker-compose.e2e.yml` (project `lithica-e2e`, secrets made by `e2e/stack.sh`): Mailpit v1.31.5 in the test stack only, read through its API; `nsfw-login` as a second server and Sardonyx on the same database and data. Cards synthetic (`e2e/cards.ts`), small ones committed, none third-party. CI runs Chromium and Firefox with no retries; WebKit was flaky on Linux CI and runs locally only.

### Intentional API changes (phases 0–3)

Everything else must stay wire-compatible: with `doc/API.md` through phase 1,
with `doc/openapi.json` since phase 2.

1. Password reset: tokens become random, single-use and expiring. The request
   and confirm endpoints keep their paths; the token format changes.
2. CORS: `Access-Control-Allow-Origin: *` replaced by a configured allowlist
   (default: same origin only).
3. Server refuses to start when `secret` is the default value.
4. A request larger than `max_upload_size` is refused with 413
   `RequestTooLargeError`; the server had no limit of its own before.
5. Requests that ended in an unhandled error (500) get the error that was
   meant: an id in the path that is not a number (400 for posts and comments,
   404 for pools) and a JSON body that is not an object (400).
6. An unknown path is 404 whatever the `Accept` header (it was 406 without
   `Accept: application/json`); a wrong method lists the allowed methods.
7. Additions for modules, nothing removed: posts have `contentKinds`,
   `GET /post/<id>/content` returns a post's extracted content, and a site's
   modules may add routes under `modules/<name>/`, post search tokens and
   post fields of their own.

### Intentional API changes (phase 4)

Additions only; nothing existing changes shape.

1. `GET /info` lists the enabled modules (`modules: [...]`). The server says
   what it exposes; branding and presentation are entirely the client's.
2. Modules may register file types of their own. A post of such a type has a
   module-owned `type` value and `mimeType`; clients that do not know the type
   must be able to ignore it (the legacy client is not required to show it).
3. Module routes appear in `doc/openapi.json`, tagged per module.
4. The `cards` module adds its routes, search tokens and post fields.

### Intentional API changes (phase 5)

1. A login token that does not work (unknown, disabled, expired, or of a
   user who does not exist) is refused with the error name
   `InvalidTokenError`, a kind of `AuthError` (was `AuthError`). The token
   of a user who does not exist is 403, as any token that does not work
   (was 404 `UserNotFoundError`). Basic authentication is unchanged.
2. Password reset tells no account from another. `GET
   /password-reset/{name}` answers 200 `{}` for an unknown account and for
   one without an email (was 404 `UserNotFoundError` and 400
   `ValidationError`), and for an account mailed within
   `password_reset_mail_interval` (new, five minutes by default), which is
   sent nothing. The mail is sent after the answer. `MailNotConfiguredError`
   is the one error left, for any name. `POST /password-reset/{name}`
   refuses an unknown account with 400 `InvalidPasswordResetTokenError` (was
   404 `UserNotFoundError`), the error and message of a wrong, used or
   expired token.

### Intentional API changes (phase 6)

1. Token values are no longer returned except on creation: the response of
   `POST /user-token/{name}` (and `POST /app-token/{name}`) has `token`; lists,
   `PUT` responses and any `fields` selection give `null`. The server keeps
   only a hash.
2. Tokens are addressed by `id`, the value never in a path: `PUT` and `DELETE
   /user-token/{name}/{id}` (and `/app-token/...`). A value there is 404 for
   `PUT` and deletes nothing for `DELETE`, which still answers `{}` for an
   unknown token. Clients log out by id.
3. New login token values are 43 characters of URL-safe base64, not UUIDs;
   existing UUID tokens keep working.
4. Additions: user tokens have `id`; app tokens and their routes (`GET
   /app-tokens/{name}`, `POST /app-token/{name}`, `PUT` and `DELETE
   /app-token/{name}/{id}`) with the privileges `app_tokens:*`;
   `appTokenRights` in `GET /info`.
5. Contract: authenticated routes never answer with a redirect (doc/API.md,
   "No redirects").

## Phase 6 — Server foundations

**Current phase.**

Goal: tokens fit for other apps, the asset model, share links, site
settings and background jobs that the later phases and the plugins build
on. Ends in release `v0.4.0`. Design:
[doc/design/decisions](doc/design/decisions/) 0001–0004, 0008 and 0011.

The API keeps its resource names: an asset is a post (`/posts`), so
existing integrations keep working. "Asset" is the
concept, "post" the resource.

### 6.1 Tokens
- [x] Login tokens stored as a hash, not in plain text; the token value is shown once, when it's created, and never returned again (intentional API change: listing tokens no longer shows their values). Existing tokens are hashed by a migration and keep working.
- [x] App tokens: named, with a set of rights that is a subset of the owner's privileges and never includes admin, users or tokens; revocable; stored hashed and shown once. Created, listed and revoked by the owner (API, and in Sardonyx's account page). Requests made with one can do only what its rights allow.
- [x] The rights an app token can carry are listed in `GET /info`, at least: read posts, cards and lorebooks; create and edit posts, cards and lorebooks; upload.
- [x] Contract: authenticated API routes never answer with a redirect (Lumiverse drops credentials on redirects). In doc/API.md, with a test over every route.

### 6.2 Kinds
- [ ] A post's `kind` field (`media`, and kinds registered by modules: `card` from the cards module), derived from its content on upload and by `reextract`; a migration fills it for existing posts.
- [ ] Modules register kinds through the registry, with the rule for which content can be which kind.
- [ ] Changing a post's kind: its own endpoint and privilege (`posts:edit:kind`), only to a kind its content supports (a PNG card may be made `media`, a plain picture can't become `card`).
- [ ] Search token `kind:`; `GET /info` lists the kinds of the site.

### 6.3 Relations and external IDs
- [ ] Typed, directed relations between posts (from, to, type), types registered by modules (e.g. `avatar-of`, `archived-from`, `embedded-in`, `gallery-of`, `expression-of`), each with an optional label (an expression's name). Separate from the engine's existing untyped relations, which stay as they are.
- [ ] API to list a post's relations, by type, with each related post's file URLs; deleting a post removes its relations.
- [ ] External IDs: (host, the host's ID) per post, several allowed, unique per host; set and removed through the API under a privilege; search token to find a post by one.
- [ ] The visibility filter (`nsfw-login`) covers both: a hidden post appears in no relation and no external-ID lookup.

### 6.4 Listed
- [ ] A post's `listed` flag, default true. Searches leave unlisted posts out unless the query says `listed:no` or `listed:any`.
- [ ] Changing it: its own privilege.
- [ ] Sardonyx's library respects it; the post page shows that a post is unlisted.

### 6.5 Share links
- [ ] A share link per post: created under a privilege, optional expiry, revocable; listed per post and per user. Stored as a hash of a random token.
- [ ] `/share/<token>`: the server checks it and lets nginx deliver the file (an internal location in the client image); revoked or expired gives 404.
- [ ] Site setting: may NSFW posts get share links (default: no).
- [ ] Tests: valid, revoked, expired and wrong token; a share link works on a `login` site without login; the post's own file links are unchanged.

### 6.6 Site settings and feature switches
- [ ] A settings API (`GET`/`PUT /settings`, administrator only): settings declared in one registry with type, default and whether they can change at runtime. `config.yaml` gives the starting values; a value changed through the API is stored in the database and wins; settings that need a restart are read-only through the API.
- [ ] The existing runtime-safe settings move onto it (`visibility`, `nsfw_tag`, `nsfw_hide_names`, `password_reset_mail_interval`, and others found safe); `GET /info` reports the effective values.
- [ ] Feature switches: pools, favourites, scores, notes, comments. A feature that is off: its API answers as a missing feature, `GET /info` lists it as off, clients hide it. Comments and scores (the engine's up/down votes) default to off; star ratings come later (decision 0009).
- [ ] Sardonyx: an admin page for the settings and switches (administrator only).

### 6.7 Background jobs
- [ ] A small job queue in the database, worked by the server process (a thread per process, jobs claimed so several processes don't run the same one), with retries and a record of failures. For work that must not run inside a request: archiving, conversions, and later others.
- [ ] `lithica-admin jobs` lists and retries jobs; an administrator API to see them.
- [ ] Tests: a job runs once with several workers, retries on failure, survives a restart.

### 6.8 Release `v0.4.0`
- [ ] `doc/UPGRADING.md` 0.3.0 → 0.4.0: hashed login tokens (values can't be listed any more) and app tokens, kinds, relations and external IDs, listed, share links and their nginx route in the client image, settings in the database and their precedence over `config.yaml`, feature switches with comments and scores off, jobs; the legacy client removed (its image, profile, LEGACY_PORT, BASE_URL). Version, images and release as for 0.3.0.

**Done when:** an app token with read-only rights can read cards and is refused an upload and the admin settings; a login token can't be read back; a card post is `card` and a picture `media`; a related, unlisted post doesn't show in the library but shows on its relation, with its label; a post is found by its external ID; a share link opens a post's file without login and stops on revoke; an administrator changes visibility and switches pools off in Sardonyx without a restart; a job runs once across two server processes.

## Phase 7 — Cards as data

Goal: cards and lorebooks are data with versions and related assets; cards
can be created from data, so the Lumiverse plugin can import a whole
library; card images are archived; cards export in several forms. Ends in
release `v0.5.0`. Design: decisions 0003, 0005, 0006, 0010 and 0011 in
[doc/design/decisions](doc/design/decisions/).

### 7.1 Card and lorebook data, with versions
- [ ] A card's data and a lorebook's data in versions, each a full compressed JSON copy, with a retention setting (all, or the last N plus version 0). For an uploaded card, version 0 is what was read from its file, which is kept untouched.
- [ ] `lorebook` as a kind (0010): a card links its books, many to many, in order; a book may stand alone.
- [ ] API: list versions, read one, restore one (a restore is a new version); writes carry the version they were based on and are refused when it's stale.
- [ ] Existing cards converted once (a background job): their embedded books become lorebooks, and books with the same content embedded in several cards become one book linked to all of them.
- [ ] Card text refers to assets by a Lithica reference the clients resolve, not by a file URL (signed URLs expire).

### 7.2 Cards created from data
- [ ] Uploads with a JSON body (base64) as a second way into the temporary upload, for clients that can't send multipart; the size limit allows for base64's third more.
- [ ] Creating a card from card data (CCv3 JSON) plus references to uploaded assets and to lorebooks, under a privilege an app token can carry; its first version is version 0, with a source note (0011).
- [ ] Creating and updating lorebooks through the API the same way.
- [ ] Duplicates by a hash of the normalised card data, for cards with and without a file; with an external ID (6.3) given, an existing card is updated (a new version) instead of a duplicate made.
- [ ] Related images with roles (6.3): avatar, gallery, alternate avatars, expressions with their labels; unlisted, with the card's safety and NSFW tag.
- [ ] Tests that a bulk import works within the limits: hundreds of cards created one after another through the API, a re-run updating instead of duplicating.

### 7.3 A card's own images
- [ ] A PNG card's picture and a CHARX's embedded images (icon, backgrounds, sprites) become unlisted posts related to the card (`avatar-of`, `embedded-in`), inheriting its safety and NSFW tag; listed with their file URLs (served with their image type).

### 7.4 Archiving card images
- [ ] Finding image links in a card's text (Markdown and HTML images, `srcset`, CSS `url()`).
- [ ] A background job (6.7) fetches them through the SSRF-safe downloader with size and type limits, makes each an unlisted post related `archived-from` the card, with the card's safety and NSFW tag, and makes a new card version pointing to them. Links that fail are recorded, and can be retried.
- [ ] Setting: manual or automatic, with rules (automatic only for given creators or tags). An "Archive images" action per card under a privilege.

### 7.5 Export and the original
- [ ] Download as: the original file (while kept), or built from the current version as PNG, CHARX or JSON, with the linked lorebooks embedded (merged in order when several, said so in the export) and the card's images as share links (6.5) or embedded (CHARX assets, data URIs in PNG/JSON).
- [ ] Deleting the original: a privilege, a warning listing what is lost, confirmation by typing the card's name; the file's checksum is kept for duplicate detection.

### 7.6 Sardonyx
- [ ] Card page: versions (view, compare, restore), the source note, the card's related images by role, its linked lorebooks, the archiving state of each image link and the "Archive images" action, the download choices, deleting the original.
- [ ] Lorebooks as pages of their own (the existing lorebook view), with their versions and the cards that link them; standalone books findable.
- [ ] The styled-text frame shows archived images from this site (its image policy gains this site's file paths; outside hosts stay behind "Load images").

### 7.7 Release `v0.5.0`
- [ ] `doc/UPGRADING.md` 0.4.0 → 0.5.0: the conversion and its duration, lorebooks as their own kind, cards from data and JSON uploads, versions and retention, archiving and its settings, export forms. Version, images, release.

**Done when:** 100 cards created from data through the API, with gallery images, expressions and one lorebook shared by ten of them, give one lorebook linked to ten cards, and a re-run changes nothing but new versions where data changed; a Chub card with images in its greetings is archived and shows them in Styled with no outside request; a card restores to version 0; a card exports as CHARX with its images and book embedded and as PNG with share links that open without login; deleting an original keeps everything but the file.
