# PLAN.md

Roadmap for turning this szurubooru fork into **Lithica**, a booru engine
with support for optional modules.
How to work is in `AGENTS.md`. Background is in `ANALYSIS.md` (local only, may be absent).

Scope: **server modernisation, phases 0–3**, ending in release tag `v0.1.0`.

Tick a box only when the task meets the definition of done in AGENTS.md.

---

## Decisions

Settled with the owner on 2026-10-10.

| Topic | Decision |
|---|---|
| Fork model | Hard fork at upstream `10ac850`. No upstream remote, no cherry-picks. Upstream is reference-only. |
| Names | Engine **Lithica** (Python package `lithica`). GitHub repo `DominykasVad/lithica`. |
| Default branch | `main`. |
| Repo structure | One repo: engine + optional modules. Engine never imports modules. |
| Server language | Python 3.13 (no Rust rewrite). |
| Packaging | uv for everything: project, lockfile, dev env, Docker build. `lithica` is a `uv_build` package, flat layout (no `src/`). |
| Web framework | Move from the custom WSGI micro-framework (`rest/`) to **FastAPI**, route by route. |
| API docs | OpenAPI generated by FastAPI; Swagger UI at `/docs`, ReDoc at `/redoc`, admin-only or disabled in production. |
| Lint / format | ruff (replaces black, isort, flake8). Committed migrations (`lithica/migrations/versions/`) are excluded, never rewritten. `T20` bans `print`; `lithica-admin` is exempt. |
| Type checking | pyright, `basic` first, raised to `strict` per module. |
| Database | PostgreSQL 17 is the only tested/shipped database. Code stays DB-agnostic (SQLAlchemy only, see AGENTS.md). |
| Base image | Debian slim + uv (replaces Alpine system packages). Images run the source from `/opt/app` via `PYTHONPATH`; the environment is in `/opt/venv`; the package itself is not installed. |
| Registry / CI | GitHub Actions. Images to GHCR, built **only on published GitHub releases**, image tag = release tag. Docker Hub workflow removed. |
| Old client | Moved to `legacy/client/`, frozen, kept for reference and as the API smoke test. |
| Module data model | One engine-owned generic table: post id + content kind + JSON payload. Modules provide extractors, auto-tagging, search fields, routes and client panels. |

### Further defaults

Confirmed by the owner on 2026-10-10.

- Debian release: `python:3.13-slim-trixie` (Debian 13).
- ASGI server: **uvicorn** (replaces waitress; `uvicorn --reload` replaces hupper).
- Image architectures: `linux/amd64` and `linux/arm64`. **`arm/v7` dropped** (pillow-heif already needed pinning for it).
- Versioning: SemVer tags `vMAJOR.MINOR.PATCH`; `v0.x` until the owner calls it stable. Fork point tagged `fork-point` at `10ac850`.
- Line length 88.
- SQLAlchemy is held below 2.1: 2.1 defaults to psycopg 3, and the driver stays `psycopg2` until a task changes it.
- Module boundary check: **import-linter** (ruff's banned-imports rule cannot express "package A must not import package B" cleanly).
- `doc/API.md` endpoint reference is retired after phase 2 in favour of OpenAPI; its narrative sections (search syntax, concepts, error model) move to `doc/`.

### Intentional API changes (phases 0–3)

Everything else must stay wire-compatible with `doc/API.md`.

1. Password reset: tokens become random, single-use and expiring. The request
   and confirm endpoints keep their paths; the token format changes.
2. CORS: `Access-Control-Allow-Origin: *` replaced by a configured allowlist
   (default: same origin only).
3. Server refuses to start when `secret` is the default value.

### Allowed dialect exceptions

None. (The signature `ARRAY` + `unnest()` and `ilike` uses are removed in phase 1.)

### Decision log

Rules: only real decisions (a choice between alternatives that later work must
respect). One line each, max ~120 characters: `date — task — decision (reason)`.
No status notes, no "left untouched", no results — those go in commit messages.
When a phase is merged, its entries are folded into the tables above or deleted.

- 2026-10-10 — 1.1 — reset tokens: SHA-256 of a 256-bit random token, one pending per user, row deleted on use
- 2026-10-10 — 1.1 — config key `password_reset_token_lifetime`, in seconds (default 3600)

## Phase 1 — Correctness, security, portability

Goal: fix the known defects on the existing framework, so phase 2 ports
correct code.

### 1.1 Security
- [x] Password reset: random token (`secrets.token_urlsafe`), stored hashed, single use, expiry (configurable, default 1 h). New table + migration. Remove `md5(secret + salt)` scheme.
- [ ] Refuse to start if `secret` is the default or empty; clear error message.
- [ ] CORS: remove the wildcard from `legacy/client/nginx.conf.docker`; add `cors_origins` config (default empty = same origin). The server, not nginx, owns CORS from phase 2 on.
- [ ] Audit token and password comparisons for constant-time compare.
- [ ] Audit `subprocess` calls (ffmpeg, ffprobe, yt-dlp) for list arguments and timeouts.

### 1.2 Time handling
- [x] Add `util.utcnow()` returning naive UTC. Replace all 27 `datetime.utcnow()` uses in non-test code. Behaviour must not change (columns stay naive UTC).

### 1.3 Database portability
- [ ] Replace `post_signature.words` (`postgresql.ARRAY` + raw-SQL `unnest()` in `func/posts.py`) with a normal child table of (signature id, position, word) and an ORM query. Migration moves existing data. Similar-post results must be identical — add a test that compares old and new query results on the test assets before removing the old path.
- [ ] Replace `ilike` in `search/configs/util.py` with `func.lower(col).like(func.lower(value))`; check index usage on Postgres (expression index on `lower(name)` if needed, created via SQLAlchemy `Index`).
- [ ] Grep gate: no `sa.text`, `text(`, `sa.dialects`, `ilike` left in `lithica/` (excluding historical migrations). Add this as a CI check.

### 1.4 Startup and background work
- [ ] Move the two boot-time "live migrations" (post signatures, MD5 checksums) to `lithica-admin backfill` commands. On startup, only log a warning if a backfill is pending.
- [ ] Upload purge: keep as a background thread for now, but it creates and closes its own session; make it safe to run in several processes (idempotent deletes).
- [ ] Remove the in-process query cache (`func/cache.py`, the cache purger middleware). If a benchmark shows a real need, propose a replacement instead.
- [ ] Disk-usage cache in `info_api`: make it per-process-safe (short TTL is fine) and document.

### 1.5 Housekeeping
- [ ] pyright `basic` reaches zero errors.
- [ ] Remove stale config: `youtube_dl` references, `python3.9` pins.

**Exit criteria:** suite green; pyright basic clean; grep gate clean; legacy
client smoke test passes; password reset tested end to end.

## Phase 2 — FastAPI migration and OpenAPI

Goal: the custom `rest/` framework is gone; the API is FastAPI with a
generated, enforced OpenAPI contract; uploads stream to disk.

### 2.1 Skeleton
- [ ] `lithica/app.py`: FastAPI app, run by uvicorn. Mount the existing WSGI app with `a2wsgi` as the fallback, so unported routes keep working.
- [ ] Session scoping: replace thread-local `scoped_session` with a `ContextVar`-scoped one, set and cleared by middleware per request. Background threads set their own scope. Add tests that two concurrent requests never share a session.
- [ ] Error handling: exception handlers that produce the existing error body (`name`, `title`, `description`, extra fields) and status codes, mirroring `facade.py`.
- [ ] Auth as a dependency (Basic, Token, anonymous), replacing `middleware/authenticator.py`. Privilege checks as a dependency factory, e.g. `Depends(require("posts:list"))`.
- [ ] Serialization: `fields=` query parameter keeps working; response models describe the full shape with all fields optional (document why in the model module).
- [ ] Startup work (config validation, logging, purge thread) moves to the FastAPI lifespan.
- [ ] Dev: `uvicorn --reload` replaces hupper; release: uvicorn with `--workers` from env (default 1 until phase 1.4 is verified multi-process safe, then raise).

### 2.2 Port routes (one router per resource, one commit per router)
For each: port handlers to sync `def` endpoints with Pydantic request models,
then rewrite that resource's `tests/api/` tests to go through FastAPI's
`TestClient` (HTTP level). Keep every existing assertion.

- [ ] info
- [ ] users, user tokens
- [ ] password reset
- [ ] tag categories, tags
- [ ] pool categories, pools
- [ ] comments
- [ ] snapshots
- [ ] uploads (temporary upload tokens)
- [ ] posts (largest; includes multipart create/update, merge, featuring, similar search)

### 2.3 Uploads
- [ ] Multipart and `contentUrl` downloads stream to a temp file; hashing, MIME detection and thumbnailing read from the file, not from a full in-memory `bytes`. Configurable max upload size, enforced by the server (and matched in nginx).
- [ ] Memory test: uploading a large video does not grow server RSS by the file size.

### 2.4 Remove the old framework
- [ ] Delete `rest/`, `facade.py`, `middleware/`, the `a2wsgi` mount and the multipart shim from phase 0.
- [ ] Entry point everywhere is `lithica.app:app`.

### 2.5 OpenAPI contract
- [ ] `python -m lithica.openapi` prints the spec; commit `doc/openapi.json`.
- [ ] CI fails if the generated spec differs from the committed one.
- [ ] Swagger/ReDoc: enabled in development; in production behind a config flag (default off) or admin-only.
- [ ] Move narrative parts of `doc/API.md` (search syntax, resource concepts, error model, auth) to `doc/`; retire the endpoint reference.
- [ ] Spot-check wire compatibility: the legacy client smoke test passes.

**Exit criteria:** no `rest/` code left; all tests green through HTTP;
OpenAPI committed and enforced; streaming uploads verified; legacy client
smoke test passes.

## Phase 3 — Module system and baseline release

Goal: the engine can host optional modules; nothing module-specific exists
yet beyond a test fixture module. Tag `v0.1.0`.

### 3.1 Module registry
- [ ] Config `modules: []` (list of module names). Registry loads `lithica.modules.<name>` dynamically at startup; unknown names fail fast.
- [ ] Module interface (a small protocol/dataclass), each part optional:
  - routers to mount (under the module's own path prefix),
  - content extractors (see 3.2),
  - auto-tag hook (extracted content → tag names, per category),
  - search field contributions (named tokens added to the post search config),
  - serializer extras (extra fields on post responses),
  - admin CLI subcommands.
- [ ] `import-linter` contract in CI: `lithica` (engine) must not import `lithica.modules`; modules must not import each other.

### 3.2 Embedded-content pipeline (engine side)
- [ ] Table `post_content`: id, post id (FK, cascade delete), `kind` (string, e.g. `dummy_v1`), `schema_version`, `payload` (`JSON` / `JSONB` variant), `extracted_at`. Index on (`post_id`, `kind`). Multiple rows per post allowed.
- [ ] Extractor contract: given MIME type and a readable file, return zero or more `(kind, payload)` results. Extractors are registered by modules and keyed by MIME type (PNG text chunks, WebP EXIF, video metadata — not PNG-only).
- [ ] Run extractors on post create and on content update (replace the post's rows); errors in one extractor are logged and do not fail the upload.
- [ ] `lithica-admin reextract [--kind K]` re-runs extractors over existing posts in batches.
- [ ] Post API exposes content kinds present (`contentKinds: [...]`) and an endpoint to fetch a post's extracted content; modules decide the public shape.
- [ ] Redaction hook: a module can mark payload fields as private (not returned to users without a privilege).

### 3.3 Proof module (tests only)
- [ ] `tests/fixtures/modules/dummy`: registers one extractor (reads a PNG `tEXt` chunk), one auto-tag, one search token, one route. Tests cover enable/disable, extraction on upload, re-extraction, search and the import boundary.

### 3.4 Release
- [ ] `doc/INSTALL.md` rewritten for Lithica (uv, Debian image, Postgres 17, GHCR images, config, modules).
- [ ] `doc/UPGRADING.md` covers szurubooru → Lithica 0.1.0 (data volume, config renames, DB upgrade).
- [ ] pyright `strict` enabled at least for `lithica/modules/` and the new pipeline code.
- [ ] Publish GitHub release `v0.1.0`; verify the GHCR image builds and `docker compose up` works from the published images.

**Exit criteria:** release `v0.1.0` published; images on GHCR; module system
proven by the test module; legacy client smoke test passes.
